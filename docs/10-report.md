## 1. なぜ CSV だけでは足りないか

電子帳簿保存法の**見読可能性**（施行規則第2条第2項第2号）は次を求める。

> 当該電磁的記録をディスプレイの画面**及び書面**に、整然とした形式及び明瞭な状態で、
> 速やかに出力することができるようにしておくこと

`docs/09-tax-research.md` 項目5 の調査で、この要件に対して**印刷可能な帳簿出力が
未実装**であることを確認している。CSV は「書面」の要件を満たす形ではない
（表計算ソフトで開いて印刷はできるが、それは利用者の環境に依存する）。

一方、税務職員のダウンロードの求めに応じる経路には**検索性のある形式**が要り、
PDF や画像だけでは認められない。つまり**両方要る**。

- **CSV** … ダウンロードの求めへの対応、他ソフトへの取り込み、利用者の再集計
- **印刷可能な形式** … 見読可能性（書面）

> **注意**: 優良な電子帳簿の適用を受けるかどうかは利用者の選択であり、
> 届出書の提出も利用者の作業である（`docs/09-tax-research.md` 項目5）。
> このソフトウェアが「要件を満たす」と名乗ることはしない（`CLAUDE.md` §10）。
> ここで言っているのは「**満たしうる形にしておく**」までである。

## 2. 出力形式の案

### 2-1. CSV

- 文字コードは **UTF-8 (BOM 付き)** を既定にする。BOM 無しだと Excel が
  Shift_JIS として開いて文字化けする（利用者が最初に踏む）。
  Shift_JIS 出力は**用意しない**——弥生連携で要求されたときに §6 で決める。
- 改行は CRLF（RFC 4180）。
- 金額は**桁区切り無しの数値文字列**（MCP の応答と同じ。`docs/07-mcp-server.md` §5）。
  Excel が勝手に数値解釈することは許容する（会計ソフトへの取り込みでは
  文字列のほうが安全なので、弥生形式は §6 で別途決める）。
- 1ファイル1帳簿。仕訳日記帳・総勘定元帳・試算表をそれぞれ別ファイルにする。

### 2-2. 印刷可能な形式は HTML にする（PDF にしない）

**PDF 生成ライブラリを依存に加えない。**

| 候補 | 却下/採用の理由 |
|---|---|
| **HTML（`@media print` 付き）** | **採用。** 依存ゼロ（文字列を組み立てるだけ）。ブラウザで開いて印刷すれば書面になり、画面表示も同時に満たす。日本語フォントの埋め込み問題が起きない |
| PDF（`printpdf` 等） | 却下。日本語を出すにはフォントを同梱するかシステムフォントに依存する必要があり、**バイナリ配布物に IPA フォント等を抱えるか、環境依存のフォント探索を書くか**の二択になる。会計の本質から遠い割に壊れやすい |
| Typst / LaTeX を呼ぶ | 却下。外部ツールの導入を利用者に強いる |

HTML なら `kaikei-report` が **`String` を返すだけ**で済み、テストも
文字列比較で書ける。

## 3. crate 構成: `kaikei-report` は I/O を持たない

```
kaikei-core / kaikei-policy / kaikei-app（既存）
        ↑
   kaikei-report   ← 追加。データ → 文字列 の変換に徹する
        ↑
   kaikei-cli（バイナリ）/ kaikei-mcp（既存）
```

**`kaikei-report` は `sqlx` にも `tokio` にも依存しない。** 入力は既に手元に
あるデータ（`Vec<JournalEntry>` / `TrialBalanceView` / `Statement` /
`LedgerPageView`）で、出力は `String`。

- DB から取ってくるのは呼び出し側（CLI バイナリ、または MCP ツール）の仕事
- そのぶん `kaikei-report` のテストは**DB を要らない**（`cargo test` が速い）
- `kaikei-e2e` が「実 DB → 出力」の通しを見る

`.github/workflows/architecture.yml` に「`kaikei-report` は `sqlx` / `tokio` に
依存しない」ステップを足す。**足したら必須チェックにも登録する**
（`CLAUDE.md` §13。ジョブを増やしても自動では追加されない）。

## 4. 出力の口: CLI と MCP の分担

| | CLI（`kaikei-cli`） | MCP ツール |
|---|---|---|
| 誰が使うか | 人間（確定申告の作業） | AI |
| 出力先 | ファイル | 応答（文字列） |
| 想定サイズ | 1年分の全仕訳（数千行） | — |

**帳簿の出力を MCP ツールにはしない**（少なくとも当面）。理由:

1. **応答に載せる量が帳簿の大きさに比例する。** 1年分の仕訳日記帳は数千行で、
   AI の文脈を食い潰す。`audit_log` は append-only なので、それが毎回残る
   （D-089 決定6 が読み取り系を要約させている理由と同じ問題が、もっと大きな
   規模で起きる）。
2. **出力の用途が「ファイルとして保存する」ことである。** 税理士に渡す、
   印刷する、他ソフトに取り込む——いずれも AI の応答を経由する必要がない。
3. CLI なら**出力先のパスを人間が決められる**。MCP サーバーにファイル書き込みの
   権限を与えると、信頼境界が変わる（現在は「DB に append する」だけ）。

代わりに、MCP からは**出力を起動できるようにしない**。人間が
`kaikei report journal --year 2026 --out ./out/` を叩く。

**決まった**: `kaikei-cli` を別 crate にした（§7 の判断1）。`kaikei-report` の
無 I/O を構造で守るためで、`architecture.yml` が両方向を検査している
（`kaikei-report` は `sqlx`/`tokio` を知らない、`kaikei-cli` は `kaikei-mcp` を
知らない）。

## 5. 青色申告決算書のデータ出力

`JpStatementPolicy` が返す `Statement` は**汎用の様式**（区分と行）であって、
青色申告決算書の**欄**に対応していない。決算書に出すには、勘定科目を
決算書の各欄（売上（収入）金額、経費の各科目、貸借対照表の各欄…）に
マッピングする表が要る。

- マッピングは `kaikei-jp-data` の YAML に置く（税区分マスタと同じ扱い。
  コードに書かない）
- **どの科目をどの欄に入れるかは税務判断を含む**（`CLAUDE.md` §10）。
  同梱テンプレートの56科目については当てはめを用意するが、利用者が科目を
  追加した場合の欄は**利用者が決める**。未マッピングの科目は
  「どの欄にも入れず、一覧して知らせる」——黙って「その他」に入れない
- 出力は**データまで**（CSV / JSON）。**PDF の様式そのものは作らない**
  （国税庁の様式を模した帳票を出すのは、様式の正確さに責任を持つことになる）

## 6. 弥生インポート形式 CSV — 仕様の調査結果（2026-08-13）

一次情報: 弥生株式会社サポート「仕訳データの項目と記述形式（他製品から仕訳データを
インポートする場合など）」
https://support.yayoi-kk.co.jp/subcontents.html?page_id=18545
および「インポートできるデータの種類と記述形式」
https://support.yayoi-kk.co.jp/subcontents.html?page_id=18586

### 6-1. 分かったこと

**1行に借方と貸方の両方を書く。** 1仕訳のデータが1行で、行末が改行コード。
項目は半角カンマ区切りで、**25項目または27項目**（取り込み不要な項目は空欄に
してカンマだけ置く）。値にカンマを含む場合はダブルクォートで囲む。

| 列 | 項目名 | 必須 | 備考 |
|---|---|---|---|
| A | 識別フラグ | ○ | 2000（伝票以外）/ 2111（1行伝票）/ 2110（複数行の1行目）/ 2100（間）/ 2101（最終行） |
| B | 伝票No. | | 複数行の場合は1行目を反映 |
| C | 決算 | | 「中決」「本決」または空白 |
| D | 取引日付 | ○ | 会計期間内 |
| E | 借方勘定科目 | ○ | 登録済みの名称と同一が推奨 |
| F | 借方補助科目 | | |
| G | 借方部門 | | スタンダード等では非対応 |
| H | 借方税区分 | ○ | 課税方式別の指定 |
| I | 借方金額 | ○ | **整数・税込金額** |
| J | 借方税金額 | | 税抜処理時は必須 |
| K〜P | 貸方の同じ6項目 | | 借方と同構成 |
| Q | 摘要 | | 半角64桁を超えるとインポート時に切り捨て |
| R | 番号 | | 手形番号等 |
| S | 期日 | | |
| T | タイプ | ○ | 0 仕訳 / 1 出金 / 2 入金 / 3 振替 |
| U | 生成元 | | 受手・支手・償却・預金・借入・一括・按分・給与・販売・会OL |
| V | 仕訳メモ | | 半角180桁超過で切り捨て |
| W | 付箋1 | | 0〜5 |
| X | 付箋2 | | |
| Y | 調整 | ○ | yes/true/on/1/-1 でチェック |

### 6-2. この形式と `kaikei` の帳簿のずれ

**1. 明細の構造が違う。** `kaikei` の仕訳は N 本の明細を持つ（消費税額の行を
含む3行仕訳、家事按分の3行仕訳）。弥生は「借方1つ＋貸方1つ」で1行を作り、
3本以上は**識別フラグ 2110 → 2100 → 2101 の複数行伝票**として表す。
**単純な写しではなく、明細の組み替えが要る。**

貸借の本数が非対称な仕訳（借方1・貸方2 など）をどう割るかは自明でない。
機械的に決められない場合があるので、**割れないものはエラーにする**
（黙って近い形に丸めない）。

**2. 金額は税込。** `kaikei` の帳簿が税込経理（`KAIKEI_TAX_MODE=inclusive`）
なら本体価額がそのまま税込なので素直に出せる。**税抜経理の帳簿では
J/P（税金額）の扱いを決める必要がある。**

**3. 摘要が半角64桁で切り捨てられる。** 日本語なら32文字。`kaikei` 側に
制限は無いので、**切り捨てが起きることを出力時に知らせる**（黙って切ると、
取り込んだ側では元の摘要が失われたことすら分からない）。

**4. 科目は「名称」で照合する。** `kaikei` は科目コードで持っているので、
勘定科目表の名称を出すことになる。弥生側に同名の科目が無ければ取り込めない。

### 6-3. まだ分からないこと（実装前に確認する）

- **文字コード。** 上記2ページのどちらにも記載が無かった。弥生の他の
  インポート機能は Shift_JIS が通例だが、**確認できていない**。
  `kaikei-report` の CSV は UTF-8 BOM 付きなので、**そのままでは通らない
  可能性が高い**（§2-1 で「弥生向けは別に作る」と決めたのはこのため）。
- **税区分コードの対応表。** 「課税方式別税区分・税計算区分一覧を参照」と
  あるだけで、値そのものは別ページにある。`kaikei-jp` の区分
  （`SALES_10` 等）との写像は**1対1とは限らない**。対応しないものは
  変換せずエラーにする（黙って近い区分に丸めない）。
- **インボイス制度への対応。** 「請求書区分、仕入税額控除は税区分と
  組み合わせた形式」との記述があるが、具体形は未確認。
- **25項目と27項目の違い。** どちらでもよいのか、製品やバージョンで
  決まるのかが読み取れなかった。
- **やよいの青色申告との差。** 同じ形式のページが `grade_id=Blue` でも
  提供されているので同一と思われるが、突き合わせていない。

### 6-4. 見積もり

**単純な CSV 出力ではない。** 明細の組み替え（複数行伝票）と税区分の写像が
本体で、それぞれ「割れない仕訳」「対応しない区分」をどう扱うかの判断を含む。
帳簿を壊さないためには、**変換できないものを黙って通さない**ことが要る。

税区分の対応表は税務判断に触れる（ある区分を別の区分として出力することは、
その取引の税務上の扱いを変えることになる）。**税理士確認の対象に含める。**

## 8. `kaikei verify` と canonical JSON（この設計案の範囲外）

`ROADMAP.md` Phase 5 の成果物にあるが、**`close_period` と共通の前工事**
（canonical JSON の定義。`docs/03-database.md` §2 の checksum 計算式が
対象とする仕訳の JSON 形が未定義）を抱えている。D-070 が「Phase 5 の
`kaikei verify` と揃える必要がある」と書いたまま未着手である。

出力（本設計案）とは独立に進められるので、別の設計として切り出す。
